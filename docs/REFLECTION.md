# REFLECTION.md — 反思报告

> 以 docs/AGENT_LOG.md、docs/SPEC_PROCESS.md 中的真实事件为证据；结论先行。本文件由项目所有者审阅定稿。

## 1. Superpowers 技能价值盘点

**发挥最大作用的三项**：`brainstorming`（10 题选型把"重点维度=可确定性断言的反馈闭环"钉死，整个 SPEC 的确定性设计由此展开）、`writing-plans`（5 步 TDD 模板 + Interfaces 区块 + 依赖图，是 21 个 subagent 零上下文工作的基础）、`subagent-driven-development`（ledger + 两阶段评审，是整套流程的骨架）。

**形式大于实质的两项**：`finishing-a-development-branch` 的"3 选项菜单"对本项目形同虚设——因为业务总览已规定 push/PR/merge 必须人工审批，最终决策路径是固定的；`systematic-debugging` 的完整流程对"Composer 绑定失效"这类 bug 是必要的，但它假设能本地复现，本项目 TUI 类 bug 只有实机才能复现（本环境非 TTY）。

**流程成本最高的环节**：两阶段评审的 fix round。T19/T22/T23 各自走了 1 轮 fix round，每轮成本约为任务本身的 60%。但回看 fix round 抓出的东西（argv 路由失效、虚假 provider 命令、过期接线表述），**没有一个是不修也行的**——成本高但每次命中。

## 2. TDD 在 AI 协作下：阻碍还是放大器？

**放大器，但有一个系统性盲区**。红绿证据对 subagent 有真实的纪律作用：T22 的 RED ③（双写文本"hello from iterumhello from iterum"）直接暴露了 brief 示例代码的语义 bug——如果实现者不先跑红，这个 bug 会进入评审才被发现。冷启动验证也证明"计划作者没走查过的测试×实现组合"是 bug 高发区。

**盲区是"测试绿 ≠ 产物可用"**：T14 的入口 no-op 与 Composer 键绑定失效，都发生在"测试全绿、CI 全绿"的前提下——前者是测试直调 `main()` 绕过入口，后者是渲染断言测不到 stdin 事件。**教训：凡是入口/交互/分发层，必须补"真实调用路径"的验证**（编译产物实跑、stdin.write 模拟），仅靠单测绿色会产生虚假安全感。这两处都写进了 AGENT_LOG 教训栏。

## 3. Subagent 驱动工作流的自主运行边界

**能自主多久**：依赖 brief 质量。brief 含逐字测试代码的机械任务（T4-T8、T25），subagent 零提问一次完成；brief 只有 prose 或语义矛盾的任务（T9 的 render 透传、T22 的 TuiApp 状态移交），subagent 会按字面实现并埋下 bug——**它们不会挑战 brief，只会忠实执行**。这正好补上冷启动验证的结论：约六成计划缺陷源于计划文本本身，而非执行者。

**最优颗粒度**：接口预定义 + 可独立测试的交付物 + 一个审查面的任务（约 40-100 行 diff）。T28+T29 合并成一次 400 行的派发虽然快（用户加急指令），但审查面过大——正常节奏下不应合并。

**偏离记录**：会话末段 task 工具派发连续失败是本流程最大的单点故障——controller 被迫本地评审并记 ledger 偏离。若 harness 不稳定，两阶段评审的"独立审查人"价值会打折扣。

## 4. SPEC/PLAN 质量与实现质量的关联

**正面案例**：Interfaces 区块真实减少了跨任务不一致。21 个任务里没有出现"函数名/签名对不上"的集成失败——唯一一次跨任务接口缺口（T9 骨架导入路径）在 T3 就被 fix round 修正进 PLAN。

**负面案例（规约不清导致偏离）**：T19 的 I1 修复——实现者按"当时"的 main.ts 如实修正 README，但 T22 随后重写了 main.ts 的 provider 组装，导致 T19 的修正变成新的失实，直到最终评审才被抓出。**教训：文档任务必须以"合并时点"的代码为唯一事实源，且依赖该代码的任务合并顺序必须在计划里可见。**

## 5. 最有效的 prompt / context 策略

1. **brief 文件而非会话历史**：把需求/代码/测试逐字写进文件，dispatch 只带路径。会话上下文污染是 subagent 偏离的主因。
2. **"先读 X 再动手"的结构**：brief → 计划 Global Constraints → 设计文档的顺序给了 subagent 正确的注意力层级。
3. **评审 prompt 里的"named-risk checks"**：明确"叫什么风险、查了什么"，比"全面检查"更有效——T22 评审的双写确认、T27 评审的 main(argv) 逐路径回归都是这么得来的。
4. **一次性多题轰炸失败**（用户 dismiss）后改为一次一题，10 题全过——决策质量与节奏直接相关。

## 6. 凭据与分发两条工程要求带来的思考

凭据要求迫使想清楚三件事：**key 的生命周期全链路**（录入回显 `*`、存储进钥匙串、展示掩码、错误信息不回显、`.env` 明示风险、`--from-stdin` 会进 shell history）；**容器与钥匙串的不兼容**（Docker 内无 OS 钥匙串，只能 `.env` 挂载 + cwd 对齐）；**测试环境与真实环境的割裂**（本机钥匙串有真实 key，测试必须 mock keyring 且防写真实配置——T27 的 R2 裁决）。

分发要求暴露的最大坑：**`bun build --compile` 与 npm 镜像的交互**（lock 渗入 npmmirror URL）、react 19 与 ink 5 的运行时崩溃（必须 18.3.1）、编译产物的 argv 形状与脚本模式不同（T22 探针实测）。这些在本机开发时全部不可见，只在产物层显形。

## 7. 重做的话会改变什么

1. **T1 就加真机冒烟任务**：入口 no-op、键绑定失效、真 TTY 渲染——三个最大问题都源于"没有真实调用路径验证"。把"编译产物实跑 + stdin 模拟"列为每个分发/交互任务的固定验证步骤。
2. **评审轮次与任务规模挂钩**：T25-T27 这类纯数据/纯函数任务，fix round 命中率低；T19/T22 这类跨层接线任务命中率高。资源应向后者倾斜。
3. **文档任务延后到功能冻结后**：T19 的教训是文档与实现并行必然过期。README 全量核对应放在所有功能合并后做一次。
4. **本地评审兜底预案**：subagent 派发失败时 controller 的本地评审要预先定义好检查单，而不是临场发挥。

## 8. 对 Superpowers 方法论的批判

它假设了四件事，本项目里三件成立、一件不成立：

- **一次性上下文充足**（成立）：brief/报告/评审包的文件化传递确实让每个 subagent 零上下文工作。
- **人类审阅在环**（成立且被证明必要）：用户逐 PR 审批 + 评审 gate 是质量底线；用户"跳过评审"的加急指令立刻换来实机 bug——证明评审不是流程装饰。
- **任务可静态分解**（成立）：冷启动验证 + 21 任务全绿是证据。
- **流程优先于交付节奏**（不成立）：当用户说"加急、跳过评审、尽快实机演示"时，技能的完整流程（brainstorming→writing-plans→SDD→两阶段评审）每一步都要用户审批与等待，与"紧急"直接冲突。本项目的实际解法是"用户指令覆盖技能"（记入 ledger 偏离）——方法论需要一个正式的"紧急模式"：保留红绿测试与合并审批，跳过评审轮次，事后补审。

**总的判断**：这套方法论交付了一个 67→101 测试全绿、25 个 PR、无一次"先实现后补测试"的项目。它的成本是节奏，收益是可信度。两者之间的权衡点，就是"跳过评审"时付出的实机 bug 代价。
